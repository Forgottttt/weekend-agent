# 第6课：从一句查询到可追溯资料，理解小型RAG

前置知识：字典、集合、循环和工具调用。本课不要求先学向量数据库。先亲手追踪一条查询怎样得到相关资料，再讨论词法检索的局限。

## 1. 模型为什么还需要检索

模型可能不知道项目里哪些地点是室内，或者不知道“预算包含哪些费用”是我们自己的规则。检索的任务是从明确的数据源找到相关材料，交给模型作为本次决策上下文。

本项目有六份很短的自编资料。模型可以调用`search_guides`拿到正文与来源ID，再在最终候选里选择引用。应用会校验引用ID，并展示资料原文。当前没有网页抓取、PDF清洗或完整知识库问答系统。

先记住这条通路：

```text
用户需求 → 检索查询 → 找相关文档 → 工具结果进入messages
                                  ↓
                         模型选择方案与引用
                                  ↓
                         应用检查来源并展示
```

## 3. 文档先变成怎样的数据

一份资料长这样：

```json
{
  "id": "g_rain",
  "title": "雨天室内安排",
  "text": "虚构教学建议：雨天优先选择室内展览馆……",
  "source": "本项目自编虚构教学资料"
}
```

`id`用于引用和定位，`title`与`text`参与检索。来源字段说明出处，但仅有source字符串不代表已经验证内容真实性。这里所有资料都明确标记为教学资料。

文档很短，所以“一份文档就是一个块”。本项目没有按512个token自动切分，也没有overlap。面试中不能把通常的RAG流程说成自己已经实现的功能。

## 4. tokenize到底做了什么

查询`雨天室内`有4个汉字。代码把相邻两个字组成一个词项：

```text
位置0与1 → 雨天
位置1与2 → 天室
位置2与3 → 室内
```

因此`tokenize("雨天室内")`得到`["雨天", "天室", "室内"]`。其中“天室”不是自然语言词语，这是字符二元组的局限。它实现简单，但不理解词义。

英文和数字部分用正则表达式提取连续片段，并转成小写。单个汉字单独保留；标点会分开中文片段。

`words = set(tokenize(query))`把查询中的重复词项去重。当前实现不会因为查询重复说三次“雨天”，就把这个词的权重乘三。

## 5. 三个容易混淆的统计量

`GuideIndex.__init__`会构造：

```python
self.counts    # 每份文档的Counter，记录每个词项出现几次
self.lengths   # 每份文档的词项总数
self.document_frequency  # 每个词项出现于几份文档
```

例如在当前索引中：

| 查询词项 | g_rain中的tf | 全库df | 解释 |
|---|---:|---:|---|
| 天室 | 1 | 1 | 在该文档出现1次，只有1份文档含它 |
| 室内 | 4 | 2 | 在该文档出现4次，共2份文档含它 |
| 雨天 | 2 | 1 | 在该文档出现2次，共1份文档含它 |

**tf是当前文档里的次数；df是包含该词的文档数量。** 室内出现4次不意味着df也是4。

`Counter`是“键→计数”的字典式对象。读取不存在的词会得到0，方便在循环里用`if not frequency: continue`跳过不匹配词项。

`g_rain`当前词项长度为59，全库平均长度为67。修改资料后数字会变化，实验会打印新的真实统计。

## 6. BM25公式逐块读，不要整段死背

我们使用的单个词项贡献可以写成：

```text
IDF = ln(1 + (N − df + 0.5) / (df + 0.5))

贡献 = IDF × tf × (k1 + 1)
       / [tf + k1 × (1 − b + b × length / average_length)]
```

这里`N=6`，`k1=1.2`，`b=0.75`是项目固定设置，未经调参比较。

分三步理解：

1. **稀有程度**：一个词几乎每篇文档都有，区分能力较小；只在少量文档中出现，更有区分作用。IDF表达这种差异。
2. **出现次数**：文档反复出现查询词，一般更相关，但价值不会无限线性增长。分母也包含tf，因此贡献逐渐饱和。
3. **长度修正**：很长的文档天然更容易包含很多词，所以通过`length / average_length`做修正。

遇到公式，先确定每个变量来自哪一行数据，再用数值代入。不要先背“稀疏检索”四个字却说不清tf是什么。

## 7. 对同一份文档手算并核对

逐项实验对g_rain打印：

| 词项 | 对该文档的贡献（四舍五入展示） |
|---|---:|
| 天室 | 1.6196 |
| 室内 | 1.7792 |
| 雨天 | 2.1917 |
| 合计 | 5.5905 |

程序内部先累加未四舍五入的浮点数，最后再保留四位。仅把展示出来的近似值相加，某些数据下末位可能有差异。

随后`search`做三件事：只保留正分数，按分数降序排序，同分时按ID稳定排序，然后取前`top_k`条。

当前“雨天室内”只匹配到两份正分文档：g_rain约5.5905、g_photo约1.0423。即便top_k=5也只返回2条。`top_k`是上限，不是必须凑满的数量。

## 8. 返回结果如何影响模型

`TripTools.search_guides`把`documents`放进工具结果。Agent用`json.dumps`把结果交回模型，因此本次检索正文真实地进入了messages。

Agent还维护`guides`字典，键为本轮实际返回的资料ID。最终JSON若写了不在这个字典中的ID，`verify_final`会拒绝。

这检查的是**来源确实检索过**。它不能证明某句自然语言结论真的被这段资料支持，也不能证明文档在现实世界正确。当前最终页面主要展示引用资料原文，尚未实现语义层面的引用忠实性评测。

## 9. 与embedding检索怎样比较

| 维度 | 当前BM25 | embedding方案的一般思路 |
|---|---|---|
| 匹配依据 | 词项重合、词频、稀有度 | 文本编码后的向量相似度 |
| 当前能否解释分数 | 能拆成每个词的贡献 | 通常不能直接拆成词项贡献 |
| 同义表达 | 没重合时可能漏掉 | 可能召回语义相关表达，仍需评测 |
| 额外组件 | 本项目标准库即可 | 需要编码模型和向量检索实现 |
| 本项目实际状态 | 已实现 | 尚未实现 |

不能说“embedding一定更好”。要固定查询和人工相关性标注，再比較Recall@k、错误召回、延迟和维护成本。六份短资料暂时用BM25可以先把数据链路讲清。

## 10. 练习与答案

**A.** 将查询改成`unmatchedxyz`，为什么返回空列表更合理？

<details><summary>答案</summary>
没有匹配词项时，所有分数为0。返回不相关文档只是在凑条数，可能误导模型。空结果应让上层知道缺少可用资料，而不是假造来源。
</details>

**B.** 同一文档把“室内”重复100次，分数会正好变成原来的25倍吗？

<details><summary>答案</summary>
不会。tf项有饱和，文档长度也改变，平均长度可能同时改变。可以在复制到临时文件的资料中实验，先不要改正式教学知识库。
</details>

**C.** g_rain得分5.5905，能说它有559%的正确率吗？

<details><summary>答案</summary>
不能。分数只用于同一查询下的排序，不是概率，也不是事实正确度。换查询后分值尺度也可能变化。
</details>

**D.** 以后接入长PDF，首先要补什么？

<details><summary>答案</summary>
先处理解析、去噪、标题层级、段落边界、来源与更新时间，再设计切块和人工相关性样本。chunk size与overlap需要用检索结果比较，不能凭空背一个“万能512”。
</details>
