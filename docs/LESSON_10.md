# 第10课：怎样证明项目有用，而不是只证明它跑过一次

前置知识：最终校验、模式切换、工具日志。本课重点是指标的定义和分母。你不需要先背一长串评测名词，而要能回答“这个数字到底证明什么”。

## 1. 先看一个容易说错的结论

系统接到100个请求，只有1个返回计划，其余全部报错。这唯一的计划通过了最终校验。

你可以说“返回计划中的约束通过率为1/1”，但不能说“任务成功率100%”。一个只统计成功返回的指标，会把其他99次失败藏起来。

因此本项目同时报告结果状态、返回计划数、通过约束的计划数、错误，以及请求成本。

## 3. 单元测试与场景评测有什么区别

单元测试偏向检查确定行为，例如35元候选遇到30元预算必须被拒绝，输入NaN必须被拒绝，401不能重试。

场景评测把一组完整请求交给系统，观察它最终有没有生成合适状态的方案，以及花了多少请求、时间。

| 检查 | 输入例子 | 关心的输出 |
|---|---|---|
| 工具测试 | 两站到达时间间隔不足 | issues包含交通不足 |
| 协议测试 | 工具调用缺少ID | 受控错误，不能继续执行 |
| HTTP集成 | POST雨天预算80 | 完整返回并可恢复 |
| 离线场景评测 | 12个表单场景 | planned/no_plan符合预期 |
| 真实模型评测 | 同一组请求走live | 状态、费用、稳定性和失败原因 |

前四类不要求真实模型API；最后一类才真正测到模型行为。

## 4. 一个case长什么样

查看JSON文件，每例有id、request和expected_status：

```json
{
  "id": "你自己新建的场景ID",
  "request": {"budget_per_person":20,"include_meal":true},
  "expected_status": "no_plan"
}
```

为什么这例的预期有依据？当前最便宜food为25元，单地点都超过20元，所以在当前定义下满足用餐的方案不可行。这是特定数据条件的推导，不等于任何一次算法返回no_plan都证明无解。

设计新用例时应先写预期及理由，再运行。不要先看程序输出，再把它抄成“标准答案”。

## 5. evaluate按什么顺序做事

1. 读取固定用例列表。
2. 建立临时数据库与PlanningService，避免污染个人会话。
3. 对每例创建新会话，防止前一例记忆影响下一例。
4. 运行同一条固定三站弱基线，检查它满足约束的情况。
5. 运行项目系统，记录actual状态、耗时、调用数和checked。
6. 异常也生成一行actual=error，不从总数里删除。
7. 汇总并写入带时间标记的outputs报告。

报告路径末尾可能带微秒，因此每次运行路径不同，不要把路径差异当成算法结果变化。

## 6. 每个指标单独定义

| 字段 | 分子或计数含义 | 比较时的分母 |
|---|---|---|
| case_count | 总场景数 | 本身就是总数 |
| passed | actual与expected相同的数量 | case_count |
| planned_count | 实际返回planned的数量 | case_count，可另报覆盖率 |
| validated_plan_count | 返回计划中约束有效的数量 | planned_count |
| baseline_valid_count | 固定行程满足约束的场景数 | case_count |
| model_calls | 所有已记录任务的模型逻辑调用数 | 可除以总场景数看平均 |
| http_attempts | 包含重试的实际HTTP尝试数 | 不能与model_calls混用 |

`passed`比较的是预期状态，并未单独衡量“用户喜欢这个路线吗”。`validated_plan_count`通常会很高，因为应用本来就拒绝无效候选；这是机制行为，不能单独宣传成高模型智能。

## 7. 跟踪4条假设样本

| 样本 | 预期 | 实际 | 状态通过？ |
|---|---|---|---|
| A | planned | planned且检查通过 | 是 |
| B | planned | error | 否 |
| C | planned | no_plan | 否 |
| D | no_plan | no_plan | 是 |

状态通过率为2/4=50%，返回计划中的检查通过率为1/1=100%。如果来源永远返回no_plan，只能通过D，得到1/4。

这就是为什么no_plan必须在评测里单独分析：它可能是正确拒绝，也可能是本来有方案却提前放弃。

## 8. 当前12例离线结果怎么解读

当前回归预期12/12通过，其中11例返回通过约束检查的计划，1例是低预算用餐无候选。demo的真实模型调用为0。

可以说：“实现并通过12个开发期离线场景回归。”不能说：“DeepSeek任务成功率100%。”后者需要真正运行live并保存对应报告。

固定三站行程是很弱的基线，用来说明约束变化后固定模板容易失败。它没有与成熟路线算法或其他Agent系统竞争，因此也不能写“性能超过主流方案”。

## 9. 延迟和成本如何正确统计

Agent的`provider_calls`表示逻辑轮次。APIProvider的`http_attempts`每次尝试发HTTP都加1，包括失败和重试。

例子：第一轮429后重试成功，第二轮直接成功，则逻辑调用2次、HTTP尝试3次。两次成功响应返回的usage可以累加；如果一次超时发生在服务端已经处理之后，账单仍可能计费，而你没有收到usage。

这次代码修复了一个问题：旧版评测发生异常时只保存错误文本，遗漏失败任务已经发生的请求数。现在Service抛PlanningError时携带计数，评测把失败任务也汇总。

已返回input/output token总量是观测值，不能据此声称等于精确账单。单次socket超时也不是整个Agent任务的总超时：多轮与重试会使总等待更长。

## 10. 接入模型后怎样逐步验证

推荐先后顺序：

```bash
python3 main.py --doctor
python3 main.py --check-api
python3 main.py --live --budget 80 --rain
```

前两个步骤的含义详见第11课。先确认单例协议和约束都正常，再主动运行：

```bash
python3 main.py --evaluate --live
```

最后一条会对12例调用真实API，不能把它当成免费的单元测试。当前项目文档不会在没有这份实测报告时填入虚构成功率。

读取报告时，把失败按格式错误、工具参数、约束冲突、接口错误、超时和提前放弃分类，比仅盯着总分更容易决定下一步修改什么。

## 11. 扩展评测，先控制变量

可以从三个独立方向扩展：

- **任务层**：预算临界值、很短时间窗口、兴趣冲突、自然语言补充要求。
- **检索层**：为查询人工标注相关资料ID，计算Recall@k，再比较BM25或新方法。
- **系统层**：限流、响应截断、进程重启、同会话并发、非法消息。

先固定输入、地点库、模型名、参数和提示版本，再比较修改前后。否则改了提示词又换模型，成功率变化就难以归因。

另外留出没有参与开发的测试集；不能只反复修这12条直到全绿，然后推断泛化很好。真实模型还应多次运行，报告波动，而不是只挑最好一次。

## 12. 练习与答案

**A.** 加一个预算37的两站边界单元测试，预期是什么？

<details><summary>答案</summary>
对于第3课固定公园+面馆且时间合法的组合，每人37应通过，36应拒绝。这是单元或业务回归；完整规划器可能选择别的路线，因此不要把两站固定结果强行当成所有Agent输出的唯一答案。
</details>

**B.** API失败的用例从rows里跳过，统计会怎样？

<details><summary>答案</summary>
分母变小，成功率被抬高；调用和成本也可能被遗漏。应保留error行，并带上已有计数。失败不是“没有发生过”。
</details>

**C.** 看到最终约束通过率100%，还能提出什么追问？

<details><summary>答案</summary>
一共多少请求？多少返回计划？多少no_plan和error？预期planned的任务完成了多少？数据是否真实？方案是否有重复、绕路或用户不喜欢的选择？有没有独立测试集？
</details>

**D.** 如果模型A更便宜但经常需要重试，怎样比较？

<details><summary>答案</summary>
比较同一批任务的最终成功、实际尝试、总延迟和观测token/账单。不能只比较每百万token单价，也不能忽略失败重跑的成本。
</details>
