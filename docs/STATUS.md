# 验证状态与已知局限

更新：2026-10-05。本文件只记录**可验证的事实**与**明确的局限**，不包含主观评价。

## 当前版本

Python 标准库实现，无第三方运行依赖，核心代码约 2700 行：

- 18 个虚构地点、固定教学天气与网格路线。
- 5 个业务工具（天气、地点筛选、路线、行程检查、资料检索）+ `submit_plan` 交付工具；JSON Schema 子集参数校验与工具注册表。
- 多站离线贪心规则流程，以及兼容 Chat Completions 的真实模型适配器。
- 工具消息配对、协议错误检查、模型轮数与工具请求上限、终审有限重试。
- 权威表单约束；最终地点与引用必须来自本轮工具结果；应用重算费用、时间与营业时段并渲染。
- 201 篇检索语料、字符二元组 BM25；不是 embedding 或向量库。
- SQLite 保存完整回合与生成快照；选最近三个完整回合给模型；会话锁与乐观版本更新。
- 仅绑定 `127.0.0.1` 的本地网页：SSE 进度流、历史列表、自然语言条件解析。
- 四套评测（agent 回归、槽位抽取、引用评审、检索对比）、GitHub Actions CI、最小 MCP stdio 服务。

## 真实模型验证

首次真实调用为 2026-10-04。此前所有"验证"均为模拟响应，没有任何真实网络请求。

- **配置事故（已修复）**：`.env` 某行缺少换行，`LLM_BASE_URL=https://api.deepseek.com` 被粘在 API key 之后。`read_env_file` 按第一个 `=` 切分，72 字符整体被当作 key，`--check-api` 返回 HTTP 401。修复为独立行后 key 还原为 35 字符（`sk-`+32 位）。**属纯配置错误，代码无需修改。**
- `--check-api`：2 次模型请求、1 次工具调用、529+107 token、1.7 秒；模型正确调用 `get_weather` 并如实说明数据为虚构教学数据。
- **Agent 回归**：改为 `submit_plan` 交付后连续 3 次 **12/12、12/12、12/12**，请求数 54–68，中位耗时 6.6–7.5 秒，**0/12 触发修复轮、0/12 走文本兜底**。
- **槽位抽取**（20 例口语化输入）：槽位准确率 **96.0%**、幻觉误填率 **1.6%**、追问触发正确率 **100%**。
- **引用评审**（12 例，LLM-as-judge）：命中率 **70.4%**、召回率 **95.0%**、无关引用率 29.6%。
- **资料检索**（201 篇 / 44 条标注查询）：BM25 recall@5 **67.0%**、MRR 0.706；TF-IDF 基线 65.9% / 0.712。两者接近，说明 BM25 的优势不是自动成立的。
- **自我修正证据**：一次真实规划中模型先提 171 元（被拒）、再提 126 元（被拒）、最终收敛到 77 元，全程只依赖 `check_itinerary` 返回的 `issues`。
- 真实调用合计约 986 次可统计模型请求、3,744,139 输入 token、192,880 输出 token，按官方价目折算约 4.5 元（空闲时段，未区分缓存命中）。

原始报告与调用 trace 固化在 `reports/`，说明见 `reports/README.md`。

## 检索与记忆的增强（2026-10-05）

四段检索链路（召回 → 融合 → 精排）全部实现，并在 44 条标注查询上做对照实验。**结论包含负面结果**：

| 方法 | recall@5 | MRR | 结论 |
|---|---|---|---|
| BM25 稀疏（基线） | 67.1% | 0.706 | 默认使用 |
| 二阶共现稠密（零依赖自造） | 11.0% | 0.048 | 独立使用无效 |
| 稀疏 + 稠密 RRF 融合 | 67.1% | 0.422 | 融合差路由拖累排序 |
| 融合 + LLM 精排 | 69.3% | 0.750 | 唯一稳定有提升 |

- **切片有效**：64 篇长文档语料上整篇检索 recall@5 58.2%，切片后 59.5%–63.9%，MRR 0.665 → 0.716–0.727。
- **重叠的反直觉结论**：重叠越多 recall@5 反而越低。实测原因是同源片段挤占 top-k——30% 重叠时 32/44 条查询出现重复父文档，去重后可覆盖文档数从 4.93 降到 3.95。加入「超额召回 + 父文档去重」（`ChunkedIndex`）后恢复到 62.5% / MRR 0.727。
- **自造稠密后端没有价值**：DeepSeek 无 embedding 接口、环境无本地模型，因此实现了零依赖的二阶共现后端；它独立召回仅 11.0%，作为补充只带来 MRR +0.011。生产路径应接真正的 embedding API（`ApiEmbeddingProvider` 已实现，但**未用真实服务验证过**）。
- **LLM 精排**：44 次模型调用、56 秒，recall +2.3pp、MRR +4.4pp，**零次编造候选外 ID**。
- **记忆分层**：结构化事实零额外模型调用（直接取自已校验的 `TripRequest`），冲突时覆盖并保留历史版本；滚动摘要需一次模型调用，默认关闭。
- **工具并行**：机制有效（合成 0.3s 慢工具 0.92s → 0.31s），但真实工具合计不到 1 毫秒，实测并发反而更慢（7.46ms vs 6.66ms），默认关闭。
- **提示注入防御**：8 类规则 + 定界符包裹，红队集 15/15 命中、3 条负样本零误报、201 篇真实语料零误报；但**语义改写、异体字、编码载荷全部绕过**（自测 3 条新样本无一挡住），且未为迎合测试而放宽规则。详见 `docs/GUARD.md`。
- **可观测性面板**：`/trace` 与 `/api/stats` 把运行数据可视化（成功率、分位耗时、token、工具直方图、失败归因、event 时间线）。

## 已修复的缺陷（排查过程见 `reports/README.md`）

1. **工具层给出假绿灯**：`check_itinerary` 不检查用餐要求，而终审检查，两层口径不一致导致模型连续三次终审失败。修复为把 `include_meal` 与 `rain` 一样作为用户级约束在构造 `TripTools` 时注入，模型无法通过工具参数放宽。
2. **最终输出不是干净 JSON**：第一次修复基于错误假设（以为只是 Markdown 围栏），只剥离围栏，结果同一用例的修复轮从 5/6 恶化到 6/6；在 `final_rejected` 事件里补记被拒原文后才发现真因是"前置解释文字 + 裸 JSON"。最终改为 `submit_plan` 工具调用，分离方案参数与解释文字；仍须进行JSON解析、Schema与业务校验，不保证所有生成参数天然合法。
3. **无解场景空转**：模型在"要求用餐但预算内没有餐厅"时反复换参数搜索，耗尽工具调用额度。修复为在无解时返回判决性 `hint`，同用例工具调用从 17 次降到 5 次。

## 已知局限

- **Agent 回归仅 12 例**，是开发期小型回归集，不是盲测，不能推断真实模型的泛化能力。
- **引用评审是模型评审模型**，评审自身有偏差；方案没有自由文本论证，因此测的是引用与方案主题的相关性支持，不是严格语义蕴含；引用条数仅 27 条，比例类指标不稳定。
- **检索语料与标签均由脚本合成**（`scripts/build_corpus.py`，固定种子），不是人工撰写或人工标注；查询只有正例、没有负例和分级相关性。recall@5 与 MRR 只反映两种词法方法在合成数据上的相对表现。
- **抽取评测仅 20 例**，标签由作者人工标注，兴趣标签的归类存在判断余地。
- **MCP 服务是最小子集**（initialize / tools/list / tools/call / ping），未实现 resources、prompts、sampling、取消与协议版本协商，且**没有用真实 MCP 客户端验证过**。
- 检索默认仍是字符二元组 BM25；**有 embedding 接口但没有可用的真实 embedding 服务**（DeepSeek 无该接口、环境无本地模型），自造的零依赖稠密后端实测无效。**没有向量数据库**；口语化近义词仍是词法检索的硬盲区。
- 会话摘要压缩已实现但**默认关闭**（需要一次额外模型调用）；结构化长期记忆只覆盖固定的出行槽位，不是通用语义记忆；工具节点中途恢复未实现。40000字符只限制恢复时选出的历史，当前回合追加输入和工具消息后未再次裁剪，并非全程token硬预算。
- 工具并行已实现但**默认关闭**：真实工具是内存计算，并发收益为负。
- 提示注入防御是**标记器不是安全边界**：语义改写、异体字、编码载荷均可绕过。
- 并发控制（同会话锁 + 全局双并发）只在单进程内有效，不是分布式锁。
