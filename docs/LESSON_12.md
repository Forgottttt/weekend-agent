# 第12课：把项目学成自己的能力，而不是背一份介绍

这课不是新增复杂功能，而是验证前十一课能否组合使用。你要练三件事：讲清楚、找得到代码、改得动。

教材和初始实现由AI协助生成。你理解了什么、亲手改了什么、实际验证了什么，需要靠之后的操作积累，不能由文档替你宣布。

## 1. 先定义“能回答”的标准

| 状态 | 表现 | 下一步 |
|---|---|---|
| 0：不会 | 只认识术语，不知道代码位置 | 回到对应课程运行实验 |
| 1：会复述 | 能背结论，但遇到反例就停住 | 手推变量并解释失败 |
| 2：会解释 | 能打开函数说明数据流和设计原因 | 做一项小改动并预测结果 |
| 3：能迁移 | 修改、测试、解释代价与边界 | 再挑战一个不同输入 |

终端练习中的分数由你自己填写。它不是系统测出来的能力认证，也不会自动改变“已掌握”的课程记录。

## 2. 一次练习怎么安排

建议按能力关卡而不是赶日期推进：

1. **5分钟**：不看代码，画出Service→Agent→Provider/Tools→Verifier的数据流。
2. **10分钟**：回答一题60–90秒，再回答两个追问。
3. **15分钟**：打开相关函数，用具体输入解释变量变化。
4. **15分钟**：做一个小改动或补一条测试，先写预期再运行。
5. **5分钟**：记录哪里卡住，下次回看哪一课。

如果总是卡在Python字典、切片或异常，先补这些基础，不必靠添加LangGraph等新名词来掩盖困难。

## 3. 90秒项目介绍怎么组织

按“问题→流程→一个关键设计→验证→边界”讲。可以把下面当作草稿，但每一句必须能定位到代码：

> 我做了一个“周末去哪玩”的小型行程Agent学习项目。用户提供时间、预算、人数和兴趣，系统通过天气、地点、路线、资料检索和行程检查五个工具生成教学方案。来源接口可以接离线规则，也可以接DeepSeek官方模型。关键设计是把表单条件保存在应用里，模型只提交地点与时间，最后重新计算预算和交通，避免模型擅自放宽限制。系统还保存完整会话，向模型只提供近期完整回合，并记录请求和工具轨迹。目前地点与天气都是虚构数据，离线回归与真实模型验证分开报告。

如果你还没有完成真实API调用，应明确说“已实现适配，正在做实测”，不要把“可以接”说成“已验证稳定运行”。

介绍完最好主动举一个你确实复现过的例子：预算30、模型选35元面馆被拒绝，再改25元小吃店。例子比堆名词更容易引出你能回答的追问。

## 4. 按模块准备三级回答

每道题都先说结论，再给代码证据，最后承认边界。

### 工具调用

- 结论：模型返回结构化请求，本地执行函数。
- 代码：`ToolRegistry.execute`验证后用允许的函数处理参数，`TripAgent.run`追加tool结果。
- 反例：arguments仍是字符串就按字典取值会失败；工具报错后不回传结果会破坏配对。
- 边界：有Schema不代表业务正确，模型还可能传一个合法但不符合用户需求的预算。

### 最终校验

- 结论：以TripRequest为权威条件，重算实际要展示的候选。
- 代码：`request.check_arguments`与`verify_final`。
- 反例：预算改999的工具调用可以成功，但表单30元的最终检查拒绝35元方案。
- 边界：约束通过不保证真实数据准确，也不保证体验最优。

### 检索

- 结论：六份短资料做字符二元组BM25，结果通过工具消息进入模型上下文。
- 代码：`tokenize`、`GuideIndex.search`和Agent收集guides的部分。
- 反例：语义相关但没有词项重合可能漏召回；来源ID有效不等于语义忠实。
- 边界：未实现embedding、reranker或长PDF切块。

### 记忆

- 结论：完整历史存SQLite，模型取最近三个完整回合。
- 代码：`select_context`、`retained`切片和`SessionStore.save`。
- 反例：最后两条可能只有tool与assistant，缺少工具请求；直接保存裁剪后的上下文会丢旧历史。
- 边界：没有跨会话语义记忆和节点中途恢复。

### API与评测

- 结论：适配器处理协议与HTTP，业务工具独立；区分逻辑调用和实际HTTP尝试。
- 代码：`APIProvider._request`、`diagnostics.check_api`、`PlanningError.metrics`。
- 反例：doctor通过仍可能401；429重试增加HTTP尝试；失败用例不能从分母消失。
- 边界：收到的usage不一定等于全部账单，离线12/12不是模型效果。

## 5. 现场任务一：手写一个允许列表

任务：不看项目，写一个只允许明确注册函数的注册表。先做最小版本，再说明正式版还缺什么。

```python
def add(a, b):
    return a + b

functions = {"add": add}

def execute(name, arguments):
    if name not in functions:
        return {"ok": False, "error": "未知工具"}
    if not isinstance(arguments, dict):
        return {"ok": False, "error": "参数必须是字典"}
    try:
        return {"ok": True, "data": functions[name](**arguments)}
    except TypeError:
        return {"ok": False, "error": "参数不匹配"}
```

这是面试练习片段，不替换正式注册表。它没有完整Schema、参数范围、有限数校验等能力。

追问：`execute("add", {"a":1,"b":2})`为什么等价于add(a=1,b=2)？传入未知name时为什么不能用eval找函数？传入a=True是否应该接受？当前教学片段不会拒绝bool，正式业务Schema为什么会？

## 6. 现场任务二：将每人预算改成全组预算

先别急着改代码。说清需求：用户输入的是全组总上限，模型和检查工具内部仍按每人费用计算，还是全部改成全组口径？

一种小改法是在输入层增加单独的全组预算字段，除以人数换算成每人上限。但必须处理金额精度，并避免同时存在两个互相矛盾的预算字段。

需要检查的文件至少包括：

- request.py：新字段、默认值、类型和权威转换。
- tools.py或最终验证：比较口径与金额精度。
- server/CLI/web：输入、标签、序列化和展示。
- 提示词与工具Schema：模型看到的单位。
- tests和eval_cases：边界例子及旧用例兼容。

面试时先提出测试：3人总预算111元、费用每人37元，应通过；总预算110元，应拒绝。不能只把网页标签改成“全组预算”，后端仍按每人算。

这是练习任务，当前项目仍使用每人预算，没有擅自把产品需求换掉。

## 7. 现场任务三：复现并解释一个错误

可以选下面任意一个，要求先预测再运行：

| 错误 | 复现入口 | 你要解释什么 |
|---|---|---|
| 交通只差1分钟 | lesson03逐站实验 | 为什么11:44不行、11:45可以 |

| 两轮上限不够修正 | lesson05修正实验 | continue之后没有第三轮 |
| 伪造引用 | lesson07攻击实验 | 本地存在不等于本轮检索过 |

能够亲手复现一个完整失败案例，比说“处理了各种边界情况”更可信。

## 8. 现场任务四：为新需求补测试

例子：要求用户指定的结束时间恰好等于最后一站结束时间时应当通过。

先明确输入：单站小吃店12:00开始，45分钟结束；用户end_time=12:45应通过，12:44应拒绝。

写测试时调用真实业务函数，断言valid及相关错误，而不是复制函数内部每一行再与自己比较。测试需要保护需求，不需要把实现抄一遍。

如果测试失败，先判断是实现错误、预期错误还是输入漏掉了别的约束。例如include_meal、室内外要求可能让另一层检查先失败，必须控制其他条件。

## 9. 对“AI写的代码”怎么回答

可以如实说：

> 初始框架和部分教材由AI协助生成。我把学习过程拆成可运行实验，自己重点理解并修改了……，用……测试验证了……。我能解释的范围是……，尚未独立完成的部分是……。

省略号必须由你后续实际完成的工作填入。不能现在直接写“我独立设计并实现整个系统”，也不能把看过讲义等同于亲手调试。

建议在[学习记录](STUDY_LOG.md)每次写一项：问题是什么、预测结果、改了哪个函数、实际结果、为什么。它比“今天学完了Agent”更有证据。

## 10. 视觉实习经历怎样连接到Agent

你已经确认的百度经历是算法工程师实习，涉及YOLO视觉模型微调以及陶瓷、管道缺陷检测。可以说明这些经历使你接触过数据、训练和模型效果验证；具体框架、样本规模和指标必须按你真实经历补充。

转向Agent时，需要补的是模型接口、工具协议、检索、状态管理和系统评测。这些可以通过当前项目展示学习与工程能力。

不能把视觉模型微调改称“LLM微调”，也不能在没有真实数据的情况下补写mAP、准确率提升或线上用户数量。

## 11. 遇到没实现的技术，怎样回答

题库补充[Q49–Q54](INTERVIEW_BANK.md#q49)覆盖MCP、LangGraph、注意力、事务、注册表和评测整理。

可采用“概念→本项目对应→未实现部分”的顺序：

- 问LangGraph：解释状态、节点、边可对应messages/request、模型/工具/校验、条件转移；明确当前是手写循环，没有使用该框架。
- 问MCP：说明工具调用协议与外部工具服务的标准连接是不同层；当前工具直接在本地注册，没有部署MCP服务器。
- 问LoRA：说明低秩参数增量的基本思想与训练对象；明确当前Agent项目没有训练语言模型。
- 问注意力：说明Q与K计算匹配权重，再对V加权，顺序约束和掩码影响可见信息；不要把会使用API说成实现了Transformer训练。

不会时明确哪部分不确定，再给出你会怎样验证。不要用更多陌生名词遮住一个具体问题。

## 13. 需求逐渐增加时的工作方式

以后你提出一个需求，我们先明确一个可观察的例子：什么输入，以前得到什么，希望以后得到什么。然后定位最小改动范围、补必要验证、记录结果。

比如“雨天不要户外”能转换成明确布尔约束；“安排得有趣”比较主观，就需要先说清偏好或评价方法。需求不明确时可以停下来澄清，不能为了实现快而悄悄替你定义。

涉及模型名、额度、API错误或不成立的技术说法，也会先指出证据。普通代码缺陷可以直接修并解释；需要你的账户配置或产品取舍时才需要你补信息。

## 14. 最后的自测，不靠勾选证明掌握

用同一条“雨天、80元、两个人、想拍照”的需求回答：

1. 哪个对象保存80元？
2. 谁决定调用search_places？
3. 模型输出的arguments什么时候从str变dict？
4. 工具结果怎样进入下一次请求？
5. 模型最后返回的费用能直接相信吗？
6. 刷新网页后从哪里恢复？
7. 请求429后重试，两个调用计数怎样变？
8. 返回no_plan能算成功吗？
9. 本次用的是虚构还是真实旅行数据？
10. 哪个环节由你亲自修改并验证过？

前九题要能指向文件和函数，第十题要能指向你的真实操作。做到这些，再结合实际API报告和个人改动更新简历，项目才逐渐成为你能在面试中拿得出手的作品。
